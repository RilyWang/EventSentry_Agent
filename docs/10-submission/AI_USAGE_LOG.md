# 第一部分：产品中的 AI 使用

## 1. AI 角色总览

| Agent | 模型 | 职责 | 是否可复现 |
|-------|------|------|-----------|
| **Collector**（采集） | glm-4-flash → 降级 glm-4.6 | 抓取 / 去重 / 要素预抽取 | 部分（LLM 判断） |
| **Analyst**（分析） | **glm-4.6** | 语义分析 / 聚类 / 卡片生成 | 部分（LLM 判断） |
| **Conversation**（参谋） | **glm-4.6** | 对话 + 工具调用 | 部分 |
| **状态机裁决** | **无 LLM** | 6 状态 13 规则 | ✅ **完全可复现** |
| **合规扫描** | **无 LLM** | 红线词 / 传闻标注 | ✅ **完全可复现** |
| **Reflector**（反思） | 无（确定性统计） | 命中率 / 争议 / 过期 | ✅ 完全可复现 |

**核心设计原则（关键）**：
> **LLM 只负责"看懂"，规则负责"裁决"。**
>
> - LLM 判断：这条消息是"确认"还是"否认"？是"事实"还是"传闻"？
> - 规则裁决：根据语义标签，确定性地产出状态与通知级别
>
> 这样既保留了语义理解的准确性，又保证**结论可复现、可审计**——满足题目"关键结论必须可追溯"的硬要求。

## 2. LLM 的三处具体用途

### 2.1 语义要素抽取（Collector + Analyst）

**输入**：一条原始消息（标题 + 摘要 + 来源）
**输出**（JSON）：

```json
{
  "theme": "股份回购",              // 必须从 18 项规范主题表中选
  "evidence_type": "fact",          // fact / opinion / speculation / rumor
  "semantics": "confirm",           // confirm / deny / substance / neutral
  "tier": "T0",                     // T0 / T1 / T2 / T3
  "event_time": null
}
```

**为什么需要 AI**：判断"这条公告是确认还是澄清"、"这句话是事实还是推测"——这是自然语言理解任务，规则无法穷举。

**验证方式**：
- 规范主题表**约束** LLM 输出域，防止自由发散
- 来源分级有**确定性域名表**（30+ 条）作为兜底，LLM 判断与规则表交叉校验
- 实测 217 条证据的类型分布合理：fact 150 / speculation 51 / rumor 13 / opinion 3

### 2.2 同一事件聚类（Analyst）

**输入**：新消息 + 该标的已有事件列表
**输出**：`{"id": 1, "assign": "existing", "event_id": "..."}` 或 `{"id": 1, "assign": "new", "theme": "..."}`

**为什么需要 AI**："收购剩余股权" / "重组审核" / "重组核查" 是否属于同一"并购重组"事件——语义判断。

**验证方式**：
- 提示词明确要求**"优先归入已有事件，避免过度拆分"**
- 实测效果：规范化前同一标的一次产出 **16-18 个碎片事件**，规范化后收敛到 **10 个规范事件**

### 2.3 卡片生成（Analyst）

**输入**：事件当前状态 + 证据列表
**输出**：headline / nature / risk_note / confidence / directions（演化方向 + 概率 + 支撑 + 风险）

**为什么需要 AI**：把分散证据归纳成可读结论，属于文本生成任务。

**验证方式**：
- 生成结果**强制过合规规则层扫描**，含红线词直接阻塞
- **性能优化**：仅在新建事件或状态跃迁时调用（仅追加证据时复用已有卡片）——LLM 调用量下降约 70%

## 3. AI 输出的验证机制（防幻觉）

| 机制 | 实现 | 位置 |
|------|------|------|
| **结构化输出约束** | 强制 JSON，附 `_extract_json` 容错解析 + `isinstance(dict)` 过滤 | `analyst_agent.py` |
| **枚举约束** | 主题限定 18 项；tier 限定 T0-T3；semantics 限定 4 值 | 提示词 |
| **规则兜底** | LLM 失败/返回异常时，用确定性规则表兜底（关键词→主题、来源→层级） | `_rule_theme` / `classify_tier` |
| **合规阻塞** | 卡片生成后必过 `compliance.check_event_payload()`，违规即标记 | `rules/compliance.py` |
| **状态裁决不走 LLM** | LLM 只给语义标签，状态由规则引擎产出，**可复现** | `rules/state_machine.py` |
| **来源强制可追溯** | 每条证据必须带 `source` + `date`，多数带 `source_url` | `evidence_items` 表 |

---

## 4. AI 使用中的"边界"（AI 不做的事）

| 禁区 | 兜底机制 | 验证 |
|------|---------|------|
| 股价预测 | 只展示历史行情 | 参谋 System Prompt 明确禁止 |
| 买卖建议 | 合规层扫描"买入/卖出/加仓/减仓/目标价"等红线词 | `compliance.py:BLOCKING_WORDS` |
| 精确概率 | 只允许"高/中高/中/中低/低" | `compliance.py:PERCENT_PATTERN` 正则拦截 |
| 传闻当事实 | T3 必须标注"未证实"，否则阻塞 | `compliance.py:check_event_payload` |
| 非公开信息 | 仅处理公开数据源 | 采集器仅接 iFinD + Serper |

# 第二部分：开发过程中的 AI 使用

## 5. AI 承担的工作

| 环节 | AI 做了什么 |
|------|------------|
| **架构设计** | 论证"为什么是 3 个 Agent 而非 1/2/4 个"（依据：单位不同/判断量不同/模型不同/失败域不同） |
| **规则实现** | 按 `EVENT_STATE_MACHINE.md` 逐条实现 6 状态 13 规则，并写自测 |
| **数据接入** | 实现 iFinD MCP 客户端、Serper 客户端，探测接口可用性 |
| **真实素材搜集** | 用 WebSearch 核实真实媒体报道，构建 10 条真实演化链案例 |
| **缺陷发现** | 通过自测与真实数据跑批，发现并修复 11 个缺陷 |
| **文档同步** | 将设计与实现的差异逐份标注 |

## 6. 开发中经 AI 发现并修复的缺陷（全部记录在 `process.md`）

| # | 缺陷 | 根因 | 发现方式 |
|---|------|------|---------|
| 1 | 所有 T0 公告被判成"未证实传闻" | 状态机要求 semantics 精确为 `confirm`，公告常被标 `neutral` | 真实数据跑批后人工核对状态分布 |
| 2 | 事件过度拆分（一季报/二季报/中期报告各成一个事件） | 主题词由 LLM 自由生成 | 观察事件列表 |
| 3 | `last_evidence_at` 时间倒退 → 误判过期 | 取"当前批次最大值"而非历史最大值 | 观察 Rule 10 异常触发 |
| 4 | LLM 返回数组 → 卡片生成崩溃 | `_extract_json` 优先匹配 `[` | 运行时异常日志 |
| 5 | SQLite database locked | 循环内新开连接 | 运行时异常 |
| 6 | **误删全部事件**（我的操作事故） | `WHERE event_id LIKE '%__'` 中 `_` 是 SQL 通配符，匹配所有行 | 删后核查数量发现归零 |
| 7 | 回放历史事件被误判过期 | 过期规则用真实当前时间对比历史日期 | 回放后核对演化链 |
| 8 | 中性官方回应被误判"官方确认" | 规则为"非否认 T0 即确认" | 核对宁德时代案例 |
| 9 | 部分标的整批失败（`'str' object has no attribute 'get'`） | LLM 偶尔返回字符串数组 | 运行日志 |
| 10 | 失败标的消息被误标已处理 → 数据丢失 | 末尾无条件标记全部 | 代码审查 |
| 11 | 版本快照重复（重跑翻倍） | 无论是否跃迁都写版本 | 重跑后核对版本数 |

**AI 生成代码的验证手段**：每个模块自带 `if __name__ == "__main__"` 自测（状态机 13 规则 + 合规 4 场景），并全部通过；再用**真实 iFinD / Serper 数据**端到端跑批核对。

## 7. AI 的能力边界与失败记录（不隐瞒）

| 问题 | 表现 | 处理 |
|------|------|------|
| **LLM 输出不稳定** | 偶尔返回字符串数组而非对象数组；偶尔 JSON 带 markdown 围栏 | 加容错解析 + 类型过滤 + 规则兜底 |
| **LLM 判定偶有偏差** | 公告的 `semantics` 被标 `neutral` 而非 `confirm` | 用规则兜底修正，并把语义域写进提示词 |
| **性能问题** | GLM-4.6 默认开思考，单次调用 8.4s，35 标的需约 3 小时 | 实测关闭思考降至 3.0s；并改为条件调用卡片生成 |
| **iFinD 新闻接口不可用** | `search_news` 恒返回 0 条 | 改用 Serper 自动采集（题目允许"引入公开权威材料并标明来源"） |
| **扶摇接口缺失** | 本环境无 skill / 无密钥 | 用 iFinD 股票工具等效替代，并如实标注 |
| **误删数据** | 我的 `LIKE '%__'` 写法清空全部事件 | 原始消息保留，重建恢复；脚本改为只读 |
