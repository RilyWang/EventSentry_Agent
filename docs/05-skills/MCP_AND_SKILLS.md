## 一、需要的 MCP 清单

### 1.1 必选（题目环境内提供）

| MCP | 用途 | 调用的工具 | 使用 Agent |
|-----|------|-----------|-----------|
| **iFinD MCP** | 主数据源：公告、新闻、研报、互动易、行业资讯 | `get_announcements` / `get_news` / `get_research` / `get_interactive_qa` / `get_company_profile` | Collector |
| **扶摇（Fuyao）** | 事件影响验证：行情、财务、估值 | `get_price_change`（事件后 N 日涨跌）/ `get_financial_indicator` / `get_company_profile` | Analyst（生成卡片时调用） |

### 1.2 增强（建议补充，非题目必需）

| MCP / 工具 | 用途 | 必要性说明 |
|-----------|------|-----------|
| **网页搜索（WebSearch MCP）** | 补充权威信源原文；传闻反向验证检索 | iFinD 新闻覆盖不全时兜底 |
| **网页抓取（Browser/Playwright MCP）** | 阅读原文全文；需登录的媒体页 | 证据链"查看原文"能力的兜底 |
| **Scheduler（定时触发）** | Collector 的 cron 触发、Reflector 的每日批处理触发 | 若平台无内置调度则需要 |

**结论：MVP 硬依赖 = iFinD MCP + 扶摇 API（2 个）；推荐补 1-2 个。**

## 二、需要封装的 Skill 清单

V1 需要 7 个 Skill：

### Skill 1：事件要素抽取（event-extraction）

- **输入：** 一条原始消息（标题 + 正文 + 来源）
- **输出 schema：**
```json
{
  "ticker": "00700.HK",
  "theme": "AI合作",
  "action": "产品测试",
  "third_party": ["DeepSeek"],
  "direction": "positive | negative | neutral",
  "event_time": "2024-03-01",
  "confidence": 0.92
}
```
- **校验：** ticker 必须在证券主数据表中存在；direction 缺失时标 `neutral`
- **失败兜底：** 抽取置信度 < 0.7 → 进入人工队列，不进入状态机

### Skill 2：同一事件聚类（event-clustering）

- **输入：** 新消息 embedding + 候选事件列表（同标的，30 天窗口）
- **处理：** 相似度 ≥ 0.82 归入；0.70-0.82 LLM 二次裁决；< 0.70 新建事件
- **特殊规则：** 核心动作对象（收购标的/合作方）不一致 → 强制拆分

### Skill 3：来源分级（source-classification）

- **输入：** 来源名称 + URL
- **输出：** T0/T1/T2/T3
- **实现：** 规则表优先；未命中走 LLM 判断 + 写入待确认表；**已确认分级来源人工锁定，LLM 不得覆盖**

### Skill 4：状态机裁决（state-arbitration）

- **输入：** 事件当前状态 + 新增证据（含层级）
- **输出：** 新状态 or 无跃迁 + 触发规则编号
- **实现：** **纯规则引擎，无 LLM 参与**，保证可复现、可追溯
- **规则全集：** 见 EVENT_STATE_MACHINE.md（6 状态 13 规则）

### Skill 5：卡片生成（card-generation）

- **输入：** 事件快照（状态 + 证据列表 + 关注节点）
- **输出：** Face 卡片 JSON / Back 卡片 JSON
- **约束：** 输出前过合规词扫描；主结论 ≤50 字；禁止"买入/卖出/目标价"
- **缓存：** 同一事件状态未变时复用已生成卡片

**Face 卡片输出 schema：**
```json
{
  "status_tag": "官方已确认",
  "nature_tag": "positive",
  "headline": "微信已接入 DeepSeek 测试，公司确认探索中，但未签正式协议",
  "risk_alert": "主要风险：合作未签正式协议，存在测试后终止可能",
  "focus_node": { "date": "2024-03-15", "description": "年报业绩会" },
  "timeline": [
    { "date": "2024-01", "label": "传闻出现", "summary": "股吧传微信将接入 AI 大模型" },
    { "date": "2024-02", "label": "媒体验证", "summary": "财新/一财报道灰度测试" },
    { "date": "2024-03", "label": "官方确认", "summary": "公司公告确认探索合作", "is_current": true }
  ],
  "confidence": "HIGH",
  "confidence_reason": "有公司公告及2家权威媒体交叉验证"
}
```

### Skill 6：对话应答（conversation-response）

- **输入：** 用户消息 + 当前事件上下文 + 对话历史
- **能力：**
  - 证据解释型追问 → 引用具体证据
  - 关联型追问 → 检索主题关联
  - 合规拒答（"该买吗"）→ 固定模板 + 引导到事件状态
  - 探索型（"最近有什么机会"）→ 检索活跃事件
- **输出：** 回复 + 推荐追问 3 条 + 引用证据 ID 列表

### Skill 7：反思校准（reflection-calibration）

- **输入：** 昨日全部跃迁事件 + 今日新证据
- **处理：** 误判检测 / 渠道命中率统计 / 高争议标记
- **输出：** 权重更新表 + 误判样本库 + 高争议事件列表
- **触发：** 每日 02:00 批处理

## 三、Agent 划分决策

### 3.1 结论：3 个 Agent

```
┌─────────────────────────────────────────────────┐
│ ① Collector（感知 Agent）—— 常驻，5 分钟周期      │
│    职责：抓取 → 清洗 → 去重 → 要素预抽取           │
│    使用：iFinD MCP / 扶摇 / WebSearch            │
│    产出：标准化 RawMessage 入队                   │
├─────────────────────────────────────────────────┤
│ ② Analyst（判断 Agent）—— 事件驱动 + 对话驱动     │
│    职责：聚类 → 定级 → 状态裁决 → 卡片生成        │
│            → 对话应答（含扶摇行情调用）            │
│    使用：Skill 2/3/4/5/6 + 向量库 + 扶摇          │
│    产出：事件状态更新 + 卡片 + 通知 + 对话回复     │
├─────────────────────────────────────────────────┤
│ ③ Reflector（反思 Agent）—— 每日 1 次批处理       │
│    职责：误判回溯 → 渠道权重校准 → 争议标记        │
│    使用：Skill 7                                 │
│    产出：校准报告 + 权重表（反哺 Analyst）         │
└─────────────────────────────────────────────────┘
```

### 3.2 为什么不是 1 个

| 维度 | 单 Agent 的后果 |
|------|----------------|
| **上下文污染** | 批量抓取的 500 条原文 + 对话的紧凑事件上下文混在一个窗口，LLM 注意力稀释 |
| **频率冲突** | 收集要 5 分钟一次，对话要秒回；单 Agent 要么收集阻塞对话，要么对话期间漏抓 |
| **失败隔离** | iFinD 超时导致整个 Agent 挂掉，对话服务一起死 |
| **成本失控** | 每条原文都进 LLM 上下文，token 成本 ×10 |
| **职责不清** | 无法单独评估"收集质量"和"判断质量"，问题定位困难 |

### 3.3 为什么不是 2 个

2 个架构（Collector + 全能 Analyst）能跑，但把反思塞进 Analyst 有两个问题：

1. **反思是写后读自己的作业**：Analyst 每日需要停下来批量回溯昨天的判断，这会抢占在线判断/对话的资源；低频批处理和实时决策的资源需求完全不同；
2. **权重校准需要独立性**：让 Analyst 自己改自己下次判断要用的权重，缺乏制衡。独立 Reflector 产出"校准报告"，Analyst 只消费结果，权责清晰。

### 3.4 为什么不是更多（6 个）

之前草稿里出现过 Orchestrator / Presenter / Memory 独立成 Agent 的设计，MVP 阶段收敛掉：

- **Orchestrator**：用状态队列 + 锁就能解决调度，不需要 LLM Agent；
- **Presenter（卡片生成）**：是 Analyst 内部的一个 Skill（Skill 5），不是独立 Agent；
- **Memory**：Analyst 读写数据库即完成记忆，不需要人格化。

**原则：只有"职责不同到需要独立上下文、独立频率、独立失败域"时才拆 Agent。**

### 3.5 三 Agent 的协作接口

```
Collector ──(RawMessage Queue)──▶ Analyst
Analyst  ──(Event State DB)─────▶ 自身下一轮 / 前端（发现 Tab + 参谋 Tab）
Analyst  ──(Notification Queue)─▶ 推送服务
Reflector──(Calibration Report)─▶ Analyst（更新渠道权重表）
           (每日 02:00，读取 Event State DB 快照)
```

## 四、Agent 配置速查

| 项 | Collector | Analyst | Reflector |
|----|-----------|---------|-----------|
| 触发方式 | cron 5min | 队列消费 + 用户对话 | cron 每日 02:00 |
| LLM 用量 | 低（预抽取可用小模型） | 高（聚类/生成/对话） | 低（规则统计为主） |
| 上下文长度 | 中（单条消息级） | 中（单事件级，紧凑） | 大（批处理，分片） |
| 超时容忍 | 高（可补偿抓取） | 低（对话需秒回，卡片可异步） | 高（离线） |
| 失败策略 | 熔断 + 补偿 | 降级（规则兜底文案） | 跳过本轮，次日补 |
